# SELF-STUDY.md — ПР №2.5

## Експеримент 1. Автоекранування (`<script>`)

Я додав товар з назвою `<script>alert(1)</script>` і відкрив `/products`.
Скрипт у браузері не виконався, вікно alert не з’явилось.

У «Переглянути код сторінки» замість тега було:

```html
<td>&lt;script&gt;alert(1)&lt;/script&gt;</td>
```

Django сам екранує значення в `{{ p.name }}`. Символи `<` і `>` стають `&lt;` і `&gt;`, тому браузер показує текст, а не запускає JavaScript.

## Експеримент 2. `DEBUG = False` і стилі

Поки `DEBUG = True`, CSS з `{% static 'products/css/style.css' %}` відкривається, сторінка оформлена.

Коли я поставив `DEBUG = False`, стилі пропали. У DevTools запит до CSS дав 404.
Причина: `runserver` віддає статичні файли лише в режимі розробки. Якщо DEBUG вимкнений, Django вважає, що статику має роздавати вебсервер (або треба `collectstatic`). Після перевірки повернув `DEBUG = True`.

## Експеримент 3. CSRF 403

На формі `/products/add` у HTML є hidden-поле `csrfmiddlewaretoken`, а в cookies — `csrftoken`.

Я прибрав `{% csrf_token %}` (і hidden-input) і натиснув «Зберегти». Django відповів **403 Forbidden**:

`CSRF verification failed. Request aborted.`  
`CSRF token missing.`

Після цього повернув тег назад. Товар без токена не зберігся.

## Чому CSRF-запит відхилено

Django захищає POST-форми від підроблених запитів з інших сайтів. Для цього в cookie кладеться `csrftoken`, а в форму — такий самий секрет у `csrfmiddlewaretoken`. Коли я прибрав тег, у POST не було токена, хоча cookie ще була. Middleware порівняв їх і побачив, що токена в тілі запиту немає. Тому запит відхилили зі статусом 403, і дані в базу не потрапили. Це якраз і є захист від CSRF: чужий сайт не зможе тихо відправити форму від мого імені, бо не підставить правильний токен.
